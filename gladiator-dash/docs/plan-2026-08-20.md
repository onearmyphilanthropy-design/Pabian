# Gladiator Dash — Technical Architecture & Zeffy Feasibility Plan

## Context

Gladiator Dash is a mud run run by a Texas A&M nonprofit student org. The current
site (gladiatordash.com) is on Wix with registration handled by a third-party
platform ("Race Entry"). A prior planning conversation (captured in
`Gladiator_Dash_Claude_Code_Handoff.md`) produced detailed product requirements
but explicitly deferred several event-design decisions (heat scheduling,
capacities, dates) and flagged that the payment platform, Zeffy, has never
actually been tested — its behavior (webhooks, Apple Pay on its checkout,
multi-runner purchases, correlation of a purchase back to our own registration)
is assumed, not verified.

This is a **greenfield project** — no code exists yet. This plan covers exactly
what was scoped for this pass: **technical architecture** and a **Zeffy
feasibility test protocol**. It deliberately does not decide heat-interleaving
rules, capacities, or dates (those remain open per the handoff doc), and does
not wireframe UI or write code. The goal is a foundation the team can start
building against once Zeffy is tested, and a concrete protocol for that testing.

Maintainers going forward are a **small, rotating team of student org members
with varying skill levels** — this pushes every choice below toward
conventional, heavily-documented, low-exotic-complexity options over anything
clever.

---

## Recommended Stack

**Next.js (App Router, TypeScript) + Postgres, deployed on Vercel-style hosting.**

- Single language/runtime (TypeScript) across frontend, backend, and
  webhook/API routes — a rotating team only has one stack to learn, and
  Next.js has the deepest tutorial/AI-assistance coverage of any current web
  framework, which matters when institutional knowledge doesn't persist year
  to year.
- A webhook receiver just needs to respond fast and be stateless — a
  serverless Route Handler does this natively. No dedicated server or queue
  needed at this event's scale; adding one would be over-engineering.
- **Database:** Postgres via **Prisma** (not Drizzle) — the schema file
  doubles as living documentation, and Prisma Studio gives non-engineers a
  GUI to inspect data without writing SQL.
- **DB hosting:** Neon (serverless Postgres, free tier, scales to zero,
  handles the spiky registration-open/race-day traffic pattern well).
  Supabase is a reasonable alternative if the team wants a bundled
  table-editor + auth system instead of Neon + Auth.js separately — minor
  choice, not load-bearing.
- **Auth (admin only, no runner accounts):** ~~Auth.js, email magic-link or
  Google OAuth restricted to an admin allowlist.~~ **Superseded 2026-08-24** —
  the org asked specifically for **username and password**, with **no "Sign in"
  link anywhere on the public site**. Auth.js still fits (Credentials provider),
  but the magic-link/OAuth recommendation is off. Hash with argon2/bcrypt, rate
  limit the route, and send `noindex`. The unlisted URL is a preference, not the
  security boundary. **Explicitly deferred by the org — do not build yet.**
- **Styling:** Tailwind + shadcn/ui.
- **Email:** Resend, for group-invite nudges and admin alerts (not required
  day one).
- **QR:** self-generated, signed token (registration ID + server-side HMAC) —
  no external dependency, works without hitting an API at scan time.
- Cost target is near-$0 on free tiers; the one caveat is Vercel's free Cron
  frequency limits — if the reconciliation-poll cadence needs are tighter
  than the free tier allows, use a free external scheduler (GitHub Actions
  scheduled workflow) rather than upgrading by default.

## Data Model

Core entities and the key design calls made to formalize the handoff doc's sketch:

- **Event** — name, venue, start/end, timezone (explicit, for DST safety),
  registration open/close, heat interval, first/last heat, default heat
  capacity, status.
- **TicketType** — event_id, name, price, category, audience (`student` |
  `non_student`), requires_heat bool, zeffy_item_ref (nullable — shape TBD
  until tested), active. **Design call:** category (`competitive` |
  `non_competitive` | `endurance` | `arena` today) should be a plain string /
  lookup value, not a hard Postgres enum — a "fun run" category is already
  under discussion, and a string column means adding it later is a data
  change, not a schema migration.
- **Heat** — event_id, category (competitive/non-competitive only — Endurance
  and Arena never get Heat rows), start_time, **slug** (explicit stable
  column like `9-30`, not derived from formatting at render time — this is
  what `/register/heat/9-30` and group-page deep links point at), capacity
  (materialized from Event default at creation, independently editable),
  active.

  **Confirmed 2026-08-24:** heats run every **10 minutes**, **no two heats run in
  parallel**, and capacity is **125**. Because nothing runs in parallel, a start time
  identifies exactly one heat, so the `slug` scheme above holds — that was the one
  arrangement that would have broken it.

  **Add a nullable `designation`** (string). Some heats are **Corps heats**, and per
  the org that is *a label shown on the heat select page only* — not a category, not a
  ticket type, and not enforced against who may pick it. A nullable label column keeps
  it out of `category`, which stays the competitive/non-competitive axis.
- **The kids' 1K — REJECTED by the org 2026-08-24.** It was under consideration as a
  seventh ticket type on its own shorter course. It is not happening. Six ticket types
  are the complete set, there is only one course, and heat listings do not need to be
  scoped by course. The string-not-enum decision for `category` stands on its own
  merits and should be kept regardless.
- **Design call — Endurance/Arena:** no synthetic Heat row for Endurance.
  Heat's purpose is "a discrete, choosable, deep-linkable, capacity-limited
  recurring slot" — Endurance has no such choice (it just starts at the first
  heat) and Arena has no time concept at all. If either ever needs its own
  capacity cap, add a nullable `capacity` field directly on TicketType rather
  than forcing a Heat row to exist.
- **Group** — event_id-scoped, name, slug (name + random suffix, avoids
  guessability), type (`official`|`custom`), created_by, active (lets admin
  hide an inappropriate group without breaking members' registrations).

  **Selection UX, confirmed 2026-08-24:** there are far too many A&M orgs and Corps
  outfits to render as a list. The registration form uses a **searchable combobox
  over existing Groups, which creates a new Group if nothing matches** — one control
  serving both "join my fraternity" and "make a group for my four friends".

  Two build requirements follow. **Search must be forgiving** — partial words,
  case-insensitive, punctuation-insensitive — so "sqd 17" surfaces "Squadron 17";
  without that, create-on-miss quietly manufactures the duplicates the combobox
  exists to prevent. And **create-on-miss needs the `active` flag to be reachable**
  by an admin, since it is also how junk and duplicate groups get in. That admin
  surface is part of the deferred admin tooling.
- **Runner** — real typed columns (not a JSON blob) since the field set is small
  and scalar. **Design call:** Runner is a per-registration snapshot in v1, not a
  deduped cross-event identity (no runner accounts exist) — kept as its own table
  specifically so a future membership feature has a clean join target without
  reworking Order/Registration.

  **The org's actual field list, confirmed 2026-08-24** (full version and caveats
  in `docs/event-rules-confirmed.md`): name, email, **shirt_size**,
  **is_first_responder** (bool), **a&m student org?** → group, **corps member?** →
  group, waiver acknowledgement, minor acknowledgement, **emergency_contact_name**,
  **emergency_contact_phone**, **health_concerns** (free text).

  Two consequences: `dob` is **not** on the org's list, so drop it — with the
  guardian-signature requirement retracted, nothing needs the runner's age; and
  `health_concerns` is sensitive data that will land in the pre-race offline export,
  so whatever policy covers it must cover that export.

  **The org and outfit questions resolve to `group_id`, not text columns** (org,
  2026-08-24). They are a **searchable select over existing Groups that creates a new
  Group when nothing matches** — see the Group entity below. This keeps one notion of
  "who are you with" instead of two, and keeps the leaderboard's counts intact.
- **Order** — buyer name/email/phone, **correlation_id** (UUID we generate
  *before* redirecting to Zeffy — the reconciliation linchpin), zeffy_transaction_id
  (nullable, unique once known), total, payment_status, promo_code,
  raw_webhook_payload (JSON, for audit/debugging an untested integration).
- **Registration** — order_id, runner_id, event_id, ticket_type_id, heat_id
  (nullable), group_id (nullable), payment_status, checked_in,
  checked_in_at, bib_number (assigned at check-in, not pre-assigned),
  waiver_status, referred_by_registration_id (nullable, self-referencing —
  see referral attribution below), zeffy_line_item_ref (nullable).
- **Waiver — CORRECTED 2026-08-20.** An earlier draft of this plan recorded
  waivers as signed in person at the check-in table, with `waiver_status` set
  as part of the bib-assignment action. **That was wrong.** The org confirmed
  waivers are **online, acknowledged during registration** — which is what
  RaceEntry does today and what we inherit by replacing it. Therefore:
  `waiver_status` is captured **at registration time, before the Zeffy
  redirect** (Zeffy's hosted checkout is not ours to add fields to), and stored
  on Registration alongside the runner data we already collect pre-payment.
  Day-of walk-ups still sign on site, so check-in must still be able to set it.

  **RESOLVED 2026-08-24 — one mechanism, a checkbox.** The org retracted the
  guardian-signature requirement ("I was wrong about the minors it is just a check
  box"). Minors are covered by an acknowledgement checkbox carrying this exact
  wording: *"I acknowledge that if I am under the age of 18, this registration and
  waiver must be completed and agreed to by my parent or legal guardian, who has
  reviewed and consented to all terms on my behalf."*

  This **simplifies the model**: `waiver_status` can be a plain accepted/not-accepted
  plus a timestamp. No acceptance-method enum, no signer identity, no signature blob,
  no separate minor branch in the UI. The paragraph below is the superseded design and
  is kept only as a record of what changed.

  ~~**Mechanism differs by runner age**, which means `waiver_status` alone is not
  enough — the record needs to capture *how* it was accepted, since the two
  paths carry different evidentiary weight. Adults: a **checkbox** (org's
  leaning, not locked). Minors: a **real guardian signature** (confirmed),
  which also implies storing the guardian's identity, not just the runner's.
  Model this as an acceptance method plus signer identity on Registration
  rather than a single boolean.~~

  The actual waiver document has not been obtained yet — it is inside
  RaceEntry's registration form, not on any public page, and will come from the
  org. Do not draft substitute waiver language.
- **PromoCode** (lightweight) — reporting only; assume Zeffy owns actual
  discount application unless testing shows otherwise.

**Deliberately not denormalized:** heat registration counts are computed via
an indexed query (Registration by heat_id + payment_status), not a stored
counter — a query that can't drift out of sync is easier for a rotating
novice team to trust than a counter that can.

## Zeffy Integration Architecture

**Flow:** ticket → heat → group → runner info all happen in our app/DB with
no Zeffy involvement. On "proceed to payment," we create a **pending Order +
unpaid Registration row(s)** first, generating a fresh `correlation_id`, then
redirect to Zeffy's own hosted checkout (not embedded — Apple Pay is not
assumed to work in an iframe). Zeffy redirects back to our `/register/confirm`
route, which looks up the Order. Asynchronously, a webhook (if Zeffy has one)
marks the Order paid — idempotently, keyed on `zeffy_transaction_id` so
duplicate delivery is a no-op. A **fallback reconciliation job** (cron)
flags any Order stuck `pending` past a threshold, since webhook reliability
is unverified — build this in from day one, not as an afterthought.

**Two real architectural forks**, both designed around rather than
prematurely resolved by guessing:

- **Fork A — who owns heat capacity, us or Zeffy?** Recommended default:
  **our DB (A1)** — we check registered count against Heat.capacity before
  ever redirecting to Zeffy, so a full heat simply isn't selectable. Small
  race risk at the last open slot, mitigated by counting pending Orders
  against capacity with a TTL that releases the hold if payment never
  completes. This keeps the group page's "17 spots remaining" (a
  differentiating feature) accurate regardless of what Zeffy can do. If
  testing shows Zeffy can also enforce capacity cleanly, treat that as a
  secondary backstop, not a replacement.
- **Fork B — who owns QR/check-in, us or Zeffy?** Recommended: **decide now
  as ours (B1)**, not test-dependent. The venue (Lake Bryan) has spotty
  connectivity and an explicit offline-export requirement — a Zeffy-owned
  check-in would need a live API call at scan time, a poor fit regardless of
  what Zeffy supports. We already generate a signed QR per Registration and
  the checked_in/bib_number fields already live on Registration.

## Zeffy Feasibility Test Plan

Set up one fake/unlisted Zeffy event with 2 fake 10-minute heats and 2 fake
ticket types, plus a test promo code, before any production build begins.

Run in this order (deviates from the handoff doc's numbering because item 2
is a hard gate):

1. **Apple Pay on Zeffy's hosted checkout — run first.** Complete a purchase
   from an iPhone/Safari. **FAIL here disqualifies Zeffy entirely** — Apple
   Pay is a hard requirement, so a failure means abandoning this plan's Zeffy
   assumptions and reconsidering a processor like Stripe.
2. **Heats-as-items.** Can 2 heats × 2 ticket types be represented as
   distinct trackable items/variants in Zeffy? Drives Fork A (a fail forces
   A1) and whether scaling to dozens of real heats is admin-UI-feasible.
3. **Handoff/pre-selection.** Does a link into Zeffy checkout land on the
   correct pre-selected item?
4. **Correlation round-trip — the most important test.** Pass a test UUID via
   URL param and/or a custom checkout field; check whether it reappears in
   the return redirect, webhook, or export. **A fail here has the largest
   architectural blast radius** — reconciliation falls back to fuzzy matching
   (email + amount + time), which is materially weaker and should push
   toward manual admin reconciliation as a first-class feature rather than a
   rare fallback. Flag a fail here to the org before building further.
5. **Post-payment data retrieval.** Check what's recoverable per field: buyer
   identity, ticket, heat, per-runner identity in multi-item purchases,
   payment status, transaction ID, promo code, custom answers.
6. **Webhook delivery.** Trigger purchase/refund/cancellation against a
   temporary logging endpoint. A fail/partial means the return-redirect
   handoff + polling fallback becomes primary, not backup — "instant
   auto-confirm" may not be guaranteed.
7. **Multi-runner-per-transaction.** One purchase, 2+ runners, different
   ticket types/heats. A fail means full reliance on our own pre-payment
   data collection stitched together via correlation_id.
8. **Promo codes.** Confirm discounting works and whether the code is visible
   post-payment.
9. **Return-redirect behavior.** Confirm a custom return URL is configurable
   and note what parameters get appended.
10. **Refund/cancellation reflection.** Refund a test transaction; check
    whether a webhook fires and/or the export reflects it.
11. **Opportunistic, not required:** whether Zeffy supports in-person/Tap-to-Pay,
    relevant to the future walk-up-registration feature — cheap to check
    while the test event already exists.

## High-Level System Structure

Conceptual modules (no file trees, no code):

- **Public marketing pages** (Home, Course, FAQ, Sponsors, About/Cause,
  Results/Photos linking to SWSH, Contact) — low-complexity, changes rarely;
  default to static generation with content edited via PR rather than
  standing up a CMS, unless the org specifically wants non-engineers editing
  copy without one.
- **Registration flow** — the ticket → heat → group → runner-info →
  (Zeffy redirect) → confirm sequence, built as a shareable/bookmarkable
  multi-step flow so heat deep-links can drop a user in mid-flow. Owns the
  pending-Order-creation step and the confirm/return reconciliation logic.
- **Group module — where the differentiating feature lives.** Public
  `/g/{slug}` pages: roster by heat time with abbreviated names, "most
  useful heat" surfacing logic — **if the group/heat-suggested slot is full,
  show it as full and surface the chronologically nearest open heat instead**
  — a join flow that re-enters registration with heat + group pre-attached,
  and share-link presentation (Web Share API with clipboard fallback). Each
  confirmed Registration gets its own personal variant of the share link
  (e.g. `/g/{slug}?r={short-code}`, short-code derived from that
  Registration's id) so a new signup's `referred_by_registration_id` can
  record *whose* share link they came through, not just which group — this
  is what powers per-sharer attribution in Reporting, not merely per-group
  counts. Concentrate the most engineering care and documentation here.
- **Admin module** (Auth.js-gated) — split by usage posture: desk admin
  (Event Config, Heat Management, Runner/Group search, Payments
  reconciliation, Reporting) for laptops pre-race; race-day admin (QR
  check-in scanner, walk-up registration, bib assignment) for phones at the
  venue, built tolerant of spotty connectivity, with the offline CSV/Excel
  export as a first-class feature.
- **API/webhook module** — Zeffy webhook receiver (idempotent, signature-verified
  if possible), cron-triggered reconciliation endpoint. Prefer Server
  Actions/co-located Route Handlers over a separate REST layer.
- **Shared/core module** — Prisma schema/client, auth config, email
  templates, QR utilities, and a **single isolated Zeffy client module**
  containing all Zeffy-specific URL-building, webhook parsing, and
  quirk-handling — everything provisional pending test results stays
  contained here rather than scattered through the registration flow.

**Critical files once implementation starts:**
- `prisma/schema.prisma` — the data model above, source of truth for every module.
- `lib/zeffy/client.ts` — isolated Zeffy-specific logic (redirect construction, correlation passthrough, webhook parsing).
- `app/api/webhooks/zeffy/route.ts` — idempotent webhook receiver.
- `app/register/**` — registration flow, pending-Order creation, `/register/confirm`, Fork A's capacity check.
- `app/g/[slug]/**` — group pages and "most useful heat" logic.

## Confirmed Feature Additions (from post-plan gap-analysis review)

Decided in a follow-up review of the plan against real-world gaps/opportunities:

- **Registered-runner counter** on the homepage, but with an
  **admin-configurable reveal threshold** (e.g. hidden entirely until 25+
  registrations) — avoids showing a discouraging low number right when
  registration opens. Large counts (1,000+) are just display formatting
  ("1,200+"), no technical concern.
- **Bragging-rights leaderboard** — a public page ranking groups by member
  count (and, once referral attribution exists, individual top-referrers
  too). Explicitly not race results/timing — pure registration-count
  gamification between orgs/friend groups.
- ~~Family / same-purchase bundle discount~~ — **cancelled by the org 2026-08-24.**
  No discount of any kind. Multi-runner Orders are unaffected; nothing is applied
  on top of them.
- **SWSH correction:** SWSH matches event photos by face, not by bib number
  — no bib-to-runner export integration is needed for it.
- **Dropped:** pre-race shirt pickup — the org confirmed the day-of shirt
  line is never more than 1 person long, not worth the added complexity.

## Existing Brand Reference (not binding — for later use)

Pulled from the live `@gladiatordash` Instagram, which is the org's actual
promo material today. This is a reference point, not a decision — the site's
final visual direction is still open and should be judged against the
audience (college students), not copied wholesale.

- **Color:** deep navy/indigo as the dominant background (not pure black);
  bright cyan/steel blue as the primary accent (big numerals, countdowns);
  red used sparingly and deliberately (finish arch, gladiator cape) as an
  urgency accent, not a primary color; brick/stone texture appears
  occasionally as a rustic background.
- **Typography:** bold, heavy, condensed/expanded all-caps sans-serif for
  headlines and numerals ("3 DAYS," "30% OFF," "RACE DAY") — sports-marketing
  impact type, built to read at a glance in a scrolling feed, not editorial.
- **Photography:** candid, outdoor, sunlit action shots — genuinely muddy,
  mid-effort, unstaged. The authenticity is the brand, not polish.
- **Tone:** gritty confidence with a wink ("WE WILL NOT BE CANCELING OUR
  EVENT DUE TO MUDDY CONDITIONS. SEE Y'ALL NEXT SUNDAY"), military-adjacent
  toughness ("One Army," gladiator helmet mark) balanced with genuine
  campus-community warmth.

## Explicitly Deferred — and Where Each Plugs In Later

- Heat interleaving rules, capacity numbers, event dates/venue, exact
  first/last heat time → all admin-configurable Event/Heat fields; no schema
  change needed once decided.
- Multi-runner default-heat UX → UI-layer decision only; Registration.heat_id
  is already independent per runner.
- Whether DOB/emergency contact/shirt size become required → validation-layer
  change on already-existing nullable columns, not a migration.
- Roster-import / org-membership feature → future Organization /
  OrganizationMembership entities with a soft link from Runner; nothing built now.
- Walk-up registration payment mechanics → same Order→payment→confirm
  pattern, staff-operated; genuinely untested (see test item 11).
- ~~**Fun run** as a new event format/ticket category~~ → closed. Its successor,
  the kids' 1K, was **rejected by the org on 2026-08-24**. `TicketType.category`
  stays a string rather than an enum anyway — cheap, and it keeps the door open
  for a format nobody has thought of yet.
